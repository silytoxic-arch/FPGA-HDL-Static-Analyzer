# GJB10157.8.6 原生判据补充恢复

目标：附件 `T-Linter.dll`，SHA-256
`60e6b52875f4d7c3fbdf494d869b3a4bcc3fdc8ee63d8620ea9614da5d6599b0`。
以下结论来自 Ghidra 12.1.4 静态反编译，不是 Windows 程序运行观察。

## `FUN_180575950` 主执行入口

入口逐个处理规则对象中 `+0xa8` 保存的常量节点，读取节点 `+0x48` 的字面量
文本，并用 `strtol` 解析引号前的十进制声明位宽。引号后的语法分支为：

- 可选 `s`/`S`；若存在，基数字符从其后一位读取；
- `b/B` 传入基数 2；
- `o/O` 传入基数 8；
- `d/D` 传入基数 10；
- `h/H` 传入基数 16；
- 无基数的 `'0`、`'1`、`'x`、`'z` 进入专门的一位二进制路径。

带 `s` 的字面量与无 `s` 字面量使用同一个 `FUN_180576130` 位宽判断入口，
所以此前将所有 signed 字面量排除没有原生依据。主入口仅在 helper 返回 `1`
时生成诊断。

## `FUN_180576130` 位宽判断

helper 的字符转换明确接受数字、`a-f/A-F`、`x/X`、`z/Z` 和 `?`。已有恢复
证明二进制路径在最终比较前不裁剪高位零；补充控制流同时证明二进制 X/Z/?
字符也各占一个编码位。因此 `2'bx11`、`2'bz01`、`1'b?1` 的源数字位数超过
声明宽度时进入返回 `1` 的路径。

对八/十/十六进制未知数字的内部特殊值及符号扩展，反编译器给出了不可靠的
`bool` 类型，暂不据此实现。产品只新增证据确定的两部分：

1. signed 且全部为普通数值数字的 b/o/d/h 字面量；
2. 含 X/Z/? 的二进制字面量，按源数字位数比较声明宽度。

原生常量节点的生产者、所有被收集的源上下文、非二进制未知数字、负号降低、
超长声明位宽和精确诊断次数仍未完全恢复；无诊断继续保持人工复核。
