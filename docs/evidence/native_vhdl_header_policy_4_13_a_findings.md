## Recovered predicate

- 构造函数调用共享规则初始化器 `FUN_18062a230`，注册规则名 `GJB9765_VHDL.4.13.a`，再把对象 vtable 改为 `0x180efab90`。
- `FUN_1805bb190` 首先检查对象 `+0x150` 的关键字容器状态；容器为空时不进入文件头判定，说明默认关键字表不能由产品自行臆造。
- 判定入口遍历当前规则保存的 VHDL 源文件/设计根，递归收集原生 AST 类型 `0x76`、`0xa7`、`0x97`，再由 `FUN_1806a2e80` 选取 `+0x214` 行号最小的节点作为截止点。既有恢复把 `0x76` 绑定为 entity、`0x97` 绑定为点分名称；结合 VHDL 上下文子句结构，产品保守映射为最早的 `library`、`use` 或 `entity`，`0xa7` 的正式枚举名仍未恢复。
- 对配置中的每个关键字记录，字节标志为零时先对关键字和候选行执行逐字节小写转换；标志非零时保持原大小写。随后从偏移零开始执行完整关键字长度的子串搜索。
- 任一前置物理行包含关键字即可满足该项；不要求该行是注释，不要求字段冒号、非空值或单词边界，关键字不能跨物理行。
- 所有缺失关键字被聚合到一次规则诊断中；没有可用前置行时进入独立的“文件头缺失”诊断路径。
- 附件只有无文件头和完整英文模板各一个例子，能证明基本正反例，不能证明示例列出的每个英文栏目都是不可配置的固定默认项。

## 产品接入

- 复用现有显式 `header-policy` / `header-keyword` 工程配置，不增加未经证实的文件名、作者、描述、修订记录等默认栏目。
- `standard gjb9765` 下，对首个可靠识别的 `library`、`use` 或 `entity` 节点之前的非空物理行执行每关键字独立大小写策略的 ASCII 子串匹配；写在上下文子句之后的注释不作为文件头。
- 规则文本明确要求文件开头有英文注释。配置未知时，产品只采用可确定的 `--` 注释引导符作为标准文本默认子判据：此前没有注释可确定违规；存在注释仍不能证明规定栏目齐全，保持人工复核。
- 显式空关键字表关闭检查；显式工程关键字表优先于上述默认子判据。
- 删除此前 VHDL 默认要求“文件名、作者、功能描述、修改记录”四字段的产品臆测，避免将示例模板误当作固定原生算法。

## 已知边界

- 原生 AST 类型 `0xa7` 的正式名称、`0x97` 点分节点与 USE 子句的完整绑定、原生全局物理行表的构建和编码转换、重复设计根、空白行细节、非 ASCII Windows ACP 转换、默认关键字配置的外部生产者以及诊断行号/文本拼接仍未完全恢复。
- 产品当前只执行 ASCII 子集；非 ASCII 行或关键字、语法错误及不能可靠定位首个设计单元的输入不作肯定判断。
- 不宣称恢复了厂商默认关键字表，也不宣称与专有 VHDL 前端完整等价。
