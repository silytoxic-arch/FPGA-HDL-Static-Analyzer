# V1.4.142 R-9-2 来源 IF 与分支顺序

本版本继续推进规则逆向和判断准确性，不调整界面或表格。对外规则编号继续严格使用官方三段式 `R-X-X` / `A-X-X`。

## 原生证据

对 `R-9-2` 主函数 `FUN_180699180` 重新进行完整定点反编译，并与共享来源 IF 收集器 `FUN_1804c5070`、类别 1/4 生产器 `FUN_1804d24a0` 联合核对，确认：

- 每个进程的关系树按类别 1 和类别 2 的完整键区间遍历；
- 每个关系对象只用自身的单一规范化时钟名建立交集集合；
- `FUN_1804bb030` 返回的内部关系记录只贡献源码行排除，不把附加边沿名加入本规则的时钟集合；
- 进程语句层的每个直接 source-linked IF 都分别建立关系；分支、CASE、LOOP 内的 IF 不作为独立关系根；
- 类别 1 按源码顺序处理全部直接 ELSIF：第一个边沿成为主关系名，后续边沿成为内部记录；
- 非边沿静态分支可以位于首边沿之前或前两个边沿之间；第二个边沿已经记录后，后续静态分支不再把类别 4 提升为类别 1；
- ELSE 中存在多个直接链接 IF 时只采用最后一个，并且只使用其主条件，不使用其 ELSIF，也不进入 CASE/LOOP 中更深的 IF。

这些结论来自附件 `T-Linter.dll` 的离线静态反编译，不代表运行附件程序。DLL SHA-256 为 `60e6b52875f4d7c3fbdf494d869b3a4bcc3fdc8ee63d8620ea9614da5d6599b0`。

新增持久化证据：`docs/evidence/native_vhdl_clock_mux_control_4_9_b_main.txt`，SHA-256 `bc0fe99c941b098695fbbecafde00bf62c3b2eb93a6323f973efd833c6296a23`。共享类别 1 与来源 IF 证据继续引用 `native_vhdl_single_clock_process_4_9_d_category1.txt` 和 `native_vhdl_single_clock_process_4_9_d_source_if_collector.txt`。

## 产品接入

- `R-9-2` 不再要求进程体第一条语句是 IF；枚举所有独立顶层来源 IF；
- 主 IF 边沿分别建立类别 2 关系，普通语句之后的直接 IF 也能被识别；
- 类别 1 处理全部直接 ELSIF，并实现静态分支相对于前两个边沿的位置状态；
- 类别 1 只把首个边沿名加入本规则集合，附加边沿只影响类别状态和关系行排除；
- ELSE 路径只分类最后一个直接链接 IF 的主条件；
- 分支、CASE、LOOP 内 IF 不作为新的关系根；
- V1.4.141 的静态动作来源、V1.4.140 的边沿先序、关系行排除、控制候选去重及 WHEN 分支保持不变。

## 新增验证

- 普通顺序语句之后的直接主 IF：建立类别 2；
- 同一进程两个独立顶层 IF：分别建立两个时钟关系；
- 静态 ELSIF 位于前两个边沿之间：类别 1；
- 静态 ELSIF 位于第二个边沿之后：保持类别 4；
- ELSE 中两个直接链接 IF：只采用最后一个；
- 所选 ELSE 链接 IF 自身的 ELSIF：不作为该关系的时钟名。

异常多块 ELSE 的专有 frontend 降级、别名、generate/configuration、包限定或扩展名称、其他嵌套动作、错误恢复和完整层次传播仍未恢复；相关无告警继续保持人工复核，不声明完整原生等价。
