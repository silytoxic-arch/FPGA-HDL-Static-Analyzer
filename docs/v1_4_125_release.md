## 原生证据闭环

- `FUN_18078cf60` 在 `FUN_18078d950`、`FUN_18078e060` 建立候选后，首先比较数据端与使能端的来源基名。
- 基名相同后，只要任一候选缺少完整的首个 AST_SELECT(0x0e)，入口就直接进入诊断。
- 只有两侧都具有完整 AST_SELECT 及其子项时，才比较 select 字段；字段相同报告，不同不报告。
- 因此 `a` 与 `a(0)` 保持基名同源，`a(0)` 与 `a(1)` 则因双方 select 不同而排除。

证据：原生入口伪代码 `ev_f8e33d32ae5161913aa98bfae7ca3373e0277480ec1fd45e5b984d740393de26`，恢复记录 `docs/evidence/native_vhdl_tristate_shared_source_4_6_h_findings.md`；附件 DLL SHA-256 为 `60e6b52875f4d7c3fbdf494d869b3a4bcc3fdc8ee63d8620ea9614da5d6599b0`。

## 产品修正

- 数据源和控制源分别保存基名与可选的单 token select。
- 先比较基名；仅当双方都有 select 时要求 select 相同。
- 一侧无 select、另一侧有 select 时不再被完整字符串比较错误排除。
- 直接二值条件同时支持字符 `'0'/'1'` 与一位字符串 `"0"/"1"`。
- 复杂索引、表达式数据/控制和其他三态编码仍不猜测。

## 新增验证
